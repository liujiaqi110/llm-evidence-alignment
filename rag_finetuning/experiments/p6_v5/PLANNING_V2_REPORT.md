# P6-v5 Planning v2：非 Oracle 证据规划（hard_dev 开发集）

> **只做推理，不改模型权重，不训练；只用 hard_dev（56 题，其中 43 道多证据题），没有使用 test_v5。**
>
> - 全部数字为自动规则评分（评分器 v4.0.1），状态 provisional，未经人工审核。
> - v2.1 是根据本轮 hard_dev 诊断做的修复，属于**开发集上的迭代结果，不能作为泛化证据**。

## 1. 结论

**真实自动规划没有追回差距**。参考目标是 3B v4 达到 35/43，实际 v2 为 17/43、v2.1 为 20/43，都**低于**原始 RAG 的 26/43。7B 也一样，规划后低于原始 RAG（17、23 对 25）。

| 版本 | 多证据完整（3B v4 / 7B） |
|---|---|
| 原始 RAG | 26 / 25 |
| Oracle：Gold + 必要事实清单（只用于诊断） | 41 / 36 |
| Planning v2（首次运行） | **17 / 17** |
| Planning v2.1（开发集诊断后修复） | **20 / 23** |

两个模型失败的原因不同：

| 模型 | 抽取 | 失败发生在哪里 |
|---|---|---|
| 3B v4 | 必要事实召回 0.87～0.89，43 道多证据题中 31 道全部抽到；但精确率只有约 0.57，一半以上是无关事实 | **生成阶段**：拿到长而杂的事实清单后，生成质量比原始 RAG 更差（v2.1 修订前只有 19/43） |
| 7B | 召回只有 0.30（v2）和 0.62（v2.1） | **抽取阶段**：抽到的事实精确率高（约 0.91），但漏抽多 |

Oracle 清单之所以有效，是因为它**又准又全**（每题 2～4 条，全部必要）。真实规划要么“全而不准”（3B），要么“准而不全”（7B），所以两者效果差别很大。

## 2. 设计与防泄漏

实现见 `scripts/planning_v2.py`。推理阶段**只读取问题和冻结输入中的原始证据**（`cid / source / doc / text`）。

1. **逐片段抽取**（每个片段调用一次模型）：输出 fact_text、条件与范围、版本与生效时间、是否含否定或例外、必要性、原文支持片段。
   - fact_id 与来源片段 ID 由代码赋予，不采用模型自报的 ID；
   - 代码核对原文依据，并丢弃资料中夹带的指令。
2. **跨片段整合**（纯代码，不调用模型）：
   - 条件或版本不同的事实不合并；一般规则、例外和矛盾的事实都保留；
   - 用 P6-v4 已冻结的规则检测器标注真冲突、版本覆盖、适用范围、触发条件和无法判断，以区分“证据不足”和“真正冲突”；
   - 不补充原文没有的事实。
3. **生成与核验**：
   - 平台 Prompt 不变，在用户消息末尾附上事实清单；
   - 代码逐项检查必要事实是否覆盖、引用 ID 是否有效、来源片段是否被引用；
   - 有遗漏时允许修订一次；修订若引入证据外数字、无效 ID，或丢掉原先已覆盖的事实，就退回修订前答案。

**防泄漏**（`rag_finetuning/tests/test_p6v5_planning_leak.py`，7 个测试，全部通过）：

| 测试 | 内容 |
|---|---|
| 冻结输入只含允许的字段 | 开发集和测试集的冻结输入，每题只有 id / question / evidence / input_sha256，证据只有 cid / source / doc / text |
| 拒绝带标注的证据 | 证据中出现任何标注字段时，直接报错 |
| 接口检查 | 推理函数只接受问题与证据，评测脚本只传这两项 |
| 哨兵测试 | 在参考答案和必要事实中放入哨兵文字，所有 Prompt 中都不出现哨兵和标注字段名 |
| 源码检查 | 规划模块的源码不读取任何标注文件 |

标注只在模型输出落盘后，由评分程序读取。

## 3. v2 → v2.1 的修复

修复依据都来自 hard_dev 逐题诊断，所以 v2.1 只是开发集上的迭代：

| 问题（v2 中观察到的） | 证据 | v2.1 修复 |
|---|---|---|
| 生成提示中“资料没有写的内容要说明资料中没有说明”诱导整体拒答 | 3B v4 有 12 个答案直接以“资料中没有说明 / 无法回答”开头 | 改为“只对确实找不到的那一部分说明，其余部分照常回答” |
| 修订防护漏洞：原答案什么都没覆盖时，修订成“资料中没有说明”也会被接受 | dv_m02、dv_m06、dv_m09 等 | 修订必须覆盖更多必要事实（或修正无效 ID），且不是整体拒答，才接受 |
| 7B 抽取提示中“完全无关输出 []”导致几乎全部返回空 | 232 次抽取中 195 次输出不超过 3 个 token；10 个片段的探针中，相关片段也返回 [] | 去掉该句并加一个格式示例；探针显示相关片段能正常抽取（`results/planning_v2/probe_7b_extract_*.json`） |
| v2 没有保存抽取原始输出和修订前答案，无法分清是生成的问题还是修订的问题 | — | v2.1 全部保存 |

| 模型 | 多证据完整 | 内容正确 |
|---|---|---|
| 3B v4 | 19/43 | 16/56 |

修订只带来小幅提升（3B +1，7B +4）。

**测量问题（如实报告）**：3B v4 会把事实清单的编号（如 `- F7：`、`[F2]`）照抄进答案，评分器把编号中的数字计为“证据外数字”。去掉编号后重新评分（`results/planning_v2/fid_artifact_sensitivity.json`）：

| 组 | 内容正确：原始 → 去掉编号 | 无依据推断题：原始 → 去掉编号 | 多证据完整 |
|---|---|---|---|
| C（v2） | 22 → 26 | 9 → 1 | 不变 |
| F（v2.1） | 16 → 24 | 19 → 5 | 不变 |

- 表中“无依据推断”一列的 3B 规划组数字**偏高**，主要来自这个问题；
- **但多证据完整这一主指标不受影响**；去掉编号后，规划组的内容正确仍低于原始 RAG（24 对 32）；
- 抄写编号本身也说明生成器在**照搬清单格式**，而不是在组织答案。

## 5. 失败归因（43 道多证据题，每题一个主因）

| 组 | 正确 | 原文有，规划器未提取 | 规划器提取正确，生成器遗漏 | 条件 / 版本 / 范围理解错误 | 生成器错误组合事实 | 疑似评分器误判 |
|---|---|---|---|---|---|---|
| C：3B v4 v2 | 11 | 7 | **13** | 2 | 7 | 3 |
| F：3B v4 v2.1 | 7 | 7 | 8 | 3 | **14**（多数是抄写编号） | 4 |
| E：7B v2 | 15 | **23** | 0 | 0 | 3 | 2 |
| G：7B v2.1 | 21 | **17** | 1 | 1 | 1 | 2 |

注：

- “正确”一列的口径要求多证据完整且内容正确，所以会小于“多证据完整”的数字；
- “提取了不相关事实”是按事实统计的，见 FACT_EXTRACTION_ANALYSIS 第 2 节；
- 逐题明细见 `PLANNING_V2_PER_QUESTION.csv`，每题有 7 组的回答、缺失事实、缺失事实是否已被抽取、主因、陈述支持和延迟。

- 弄坏的题中有不少原本简单的两片段题（如 dv_m07、dv_m08、dv_m13、dv_m14），**规划流程对简单题有明显副作用**。
- 顺序对照题在规划后也没有变稳定：如 dv_m01 修好了，dv_m01r 却弄坏了。

## 7. 验收检查（对照指令第 6 节）

| 检查项 | 结果 |
|---|---|
| 3B v4 多证据完整 ≥ 35/43 | **否**（v2 为 17，v2.1 为 20） |
| 内容正确率是否下降 | 是（32 → 22 / 16；去掉编号后为 26 / 24） |
| 引用支持是否变差 | 3B 是（陈述支持 42 → 23 / 24）；7B v2.1 反而提高（18 → 28） |
| 无依据推断是否增加 | 3B 增加，但大部分是抄写编号造成的；去掉编号后 1 → 1 / 5 |
| 延迟是否值得 | 否。3B 中位延迟 11.5 s → 64～69 s（约 6 倍）；7B 4.8 s → 7.6～12.2 s |
| 改善是否集中 | 改善本身就很少，没有集中在某一文档或题型 |

**结论**：没有达到参考目标，而且明显退化。按指令，下一步要先区分规划提取问题与答案生成问题，再决定是否需要 DPO，见 `NEXT_EXPERIMENT_DECISION.md`。**Oracle 的 41/43 不能当作线上可达到的准确率。**
